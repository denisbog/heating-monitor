# monitoring-worker

Cloudflare Worker (Rust / `workers-rs` 0.8.7) that polls both heating clouds every
15 minutes, stores readings in D1, and serves a JSON API plus a static chart page.

Protocol research lives in `../docs/api-research.md`.

## API access levels

Two bearer tokens, both passed as `Authorization: Bearer <token>`:

| token | secret | can |
|---|---|---|
| `API_TOKEN` | long random (generated) | read **and** `POST /api/collect` |
| `READ_TOKEN` | `1013` (deliberately simple, shareable) | read only — `POST /api/collect` returns **403** |

Every GET endpoint (`/api/health`, `/api/devices`, `/api/latest`, `/api/readings`,
`/api/daily`, `/api/runs`, `/api/metrics`, `/api/ingest/series`, `/api/whoami`,
`/api/config`) accepts either token. Missing or wrong → `401`; the read-only token
gets `403 read-only token: collection not permitted` on `/api/collect` and
`403 read-only token: admin access required` on `PUT /api/config` and on the
`/api/ingest/devices` + `/api/ingest/samples` operator endpoints.

The chart page stores whatever token you paste and surfaces the 403 inline if you press
**Collect now** with the read-only one. It also calls `GET /api/whoami` on load: for the
read-only token it hides the **Collector runs** table and the **Latest values (raw)**
details (and does not fetch `/api/runs` or `/api/latest`); the admin token sees them.
`READ_TOKEN` defaults to `1013`; override with the
`READ_TOKEN` environment variable when running `make-dev-vars.sh`.

## Chart layout admin

`/admin` is a small editor for the dashboard: it sets **how many charts** the
page shows and **what each one plots** — device, metric list, unit, and a
line / area / bar style. The layout is one JSON row in the `settings` table
(`key = 'dashboard'`), so it applies to every client, not just one browser.

Each chart has a **source**:

- `cloud` (default) — the provider readings: heat pump and thermostats, from
  the `readings` / `daily` tables
- `ingest` — the samples the eink-x devices push to `POST /v1/samples`, from the
  `samples` table. The metric list is the three sensor columns the firmware
  sends: `temperature` (°C), `humidity` (%) and `battery` (V), and the device
  list is the operator-registered `ingest_devices` rows

An ingest chart also has a **timeline**, because every sample carries two
timestamps and only the user can say which one is the meaningful x axis:

| `time` | column | meaning |
|---|---|---|
| `received` (default) | `samples.received_at` | server clock at upload — the canonical, trustworthy time |
| `device` | `samples.device_collected_at` | the untrusted clock the firmware reported when it queued the sample (HR-202) |

The two differ when a device uploads a backlog: `received` puts the whole batch
at upload time, `device` spreads it over the times the samples were actually
taken. Samples with no device clock are skipped in the `device` view rather
than pretending they were taken at upload time. Both timelines are available
per chart, so one dashboard can show "when did it arrive" next to "when was it
measured".

### Splitting by node

One mesh device reports samples under several `node_id`s (a hub plus its sensor
nodes), so every ingest series is one `(device, node, metric)` line. The chart
editor makes that explicit:

- **Node = all (empty)** — split by node: each node becomes its own series,
  named `temperature · node 7` when the device has more than one node.
- **Node = 7** — only node 7's data is plotted. The series keeps the node label
  so two single-node cards stay distinguishable.

The filter is applied in the browser, not in the API: the page fetches each
timeline once and every chart shares it, so a dashboard with ten per-node cards
still costs one request. `GET /api/ingest/series` always returns `node_id` with
each row, which is enough for any other client to split or filter the same way.
The editor renders the Node choice as a dropdown: the registry's `node_id`, the
nodes in the newest samples already loaded on the page, and any node the saved
layout already uses. A node that has not uploaded since the page loaded stays
selectable, so editing an old chart never silently resets its filter.

The chart data endpoint is `GET /api/ingest/series`:

```
GET /api/ingest/series?device=&from=&to=&time=received|device&bucket=
→ [{device_id, device_name, node_id, metric, ts, value, unit}, …]
```

It returns the long `(device, metric, ts, value, unit)` shape the chart page
already renders. Points are bucketed server-side (a "nice" step — 15 min, 1 h,
1 d … — chosen from the window, ≤ 720 points, overridable with `bucket` in
seconds and clamped to ≤ 2,000 buckets), so a 90-day view costs one bucketed
query instead of 129k points. One
scan feeds all three metrics. It accepts **either token**: unlike the admin
registry below it returns measurements and registry names only — no keys, IPs or
firmware versions — but it does expose device ids (BLE addresses) to the
read-only share. That is the deliberate trade-off that lets a read-only client
see an ingest chart at all.

Without a saved layout the automatic dashboard shows the cloud charts as before
and adds an **Ingested sensors** section (upload time), one card per device and
unit. An ingest-only layout never fetches the cloud endpoints and a cloud-only
layout never fetches the samples, so each dashboard pays only for what it plots.

The layout mechanics:
- the page keeps the admin token in `localStorage` (`adminToken`, falling back
  to `apiToken`) and calls `GET /api/whoami` to tell admin from read-only
- `GET /api/config` (any token) is what the chart page reads on load; with no
  saved layout it falls back to the automatic per-device / per-unit charts
- `PUT /api/config` (**admin token only**) stores the layout — the Worker trims
  strings, caps it at 24 charts × 12 metrics, and drops charts with no metrics
- `GET /api/metrics` lists every `(device, metric, unit)` that exists, which is
  what populates the metric pickers — read from the `latest` / `daily` rollups,
  not by scanning `readings` (see "D1 read budget" below)

The same page manages the **ingest device registry** (see "Device ingest"): list,
register, edit, enable/disable, rotate the key, unregister, and — from the v2
telemetry — shows per device *last upload* (`last_seen`, server clock) vs *last
sample* (`last_sample_at`, device clock), the device clock offset, and the
accepted/rejected counts, plus a table of the newest stored samples with both
timestamps. Every one of those
calls needs the admin token, because the table holds per-device keys and the last
seen IP:

| endpoint | purpose |
|---|---|
| `GET /api/ingest/devices` | registry rows; the key is never included |
| `POST /api/ingest/devices` | register `{id, name?, role?, node_id?, period_min?, key?}` — 32 random bytes are generated when `key` is omitted, and returned **once** |
| `PUT /api/ingest/devices/:id` | edit `name`, `role`, `node_id`, `period_min`, `disabled` (empty/0 clears) |
| `DELETE /api/ingest/devices/:id` | unregister; stored samples are kept |
| `POST /api/ingest/devices/:id/key` | rotate (or set) the key, returned once |
| `GET /api/ingest/samples?device=&limit=` | newest stored samples (limit ≤ 200) for the page's *Recent samples* table |

Keys are write-only by design: the server can authenticate a device but cannot
show its key later, so the page shows it exactly once and the operator copies it
into the device's BLE config.

The schema is idempotent and its tail backfills the derived tables, so re-apply it
whenever a `CREATE TABLE` is added (it is safe to run on a live database):

```bash
wrangler d1 execute monitoring --file=schema.sql --remote
```

`ADD COLUMN` cannot be expressed idempotently in SQLite, so deltas that change an
existing table live in `migrations/` and are applied once by wrangler:

```bash
wrangler d1 migrations apply monitoring --remote
```

`migrations/0001-ingest-v2.sql` is the v2 delta (`samples.device_collected_at`,
`batches_meta`, the `ingest_devices` telemetry columns and a backfill of the
counters). `migrations/0003-sample-clock-index.sql` adds the two
`device_collected_at` indexes the device-time timeline needs (it is idempotent,
and `schema.sql` already carries the same `CREATE INDEX IF NOT EXISTS`
statements). `schema.sql` already carries the final shape for a fresh database,
so a new deployment needs only that one.

## D1 read budget

Reads — not writes — dominate the free plan (5 M rows read/day; each cron run
writes a few dozen rows). `rows_read` counts every row a query *scans*, so
aggregating 15-minute samples on every request was the whole cost:

| endpoint | before | after |
|---|---|---|
| `GET /api/latest` | 83,465 | **84** |
| `GET /api/metrics` | 166,596 | **3,412** |
| `GET /api/daily` (90 d, one device) | 48,063 | **728** |

Both derived tables are maintained at write time instead of at read time:

- **`latest`** — one row per `(device_id, metric)` with the newest sample.
  `insert_readings()` upserts it in the same call; the `DO UPDATE` only fires for
  a newer sample (or the same timestamp with a different value), so a backfilled
  older sample changes nothing. Serves `/api/latest` and the `last_ts` of
  `/api/metrics`.
- **`daily`** — per `(device_id, metric, unit, day)` `MIN`/`MAX`/`SUM`/`COUNT`,
  with `avg` computed as `vsum / n` at read time. `refresh_daily()` rebuilds a
  day range from raw `readings` instead of accumulating, so re-polled history can
  never double-count. It runs on the hourly branch of the cron (the same gate as
  the provider history pulls), covering the last two days.

Two details worth knowing before changing them:

- the rebuild uses `INDEXED BY idx_readings_ts`; without statistics the planner
  otherwise falls back to scanning all of `readings` every hour;
- a run that adds samples to a day with no rollup row yet (history pulled after
  an outage) widens that window to the oldest such day, which is how old days
  reach `/api/daily` without scanning the whole table.

`/api/daily` now answers in whole days: a request whose `from`/`to` cut through a
day gets that whole day's aggregate (the old query summed only the part of the
day inside the window). `SUM`/`COUNT` are taken over the same rows, so `min`,
`avg`, `max` and `n` are otherwise identical.

### Ingest series

`/api/ingest/series` has no rollup table to lean on: it scans the `samples` rows
inside the requested window once and buckets them. The cost is therefore
proportional to *stored samples in that window*, not to the table:

| view | window | rows scanned | rows returned |
|---|---|---|---|
| one device, 24 h @ 5 min | 24 h | ~288 | ≤ 720 buckets × 3 metrics |
| all devices, 7 d @ 5 min | 7 d | ~2,016 per device | ≤ 720 × 3 per device |

The window is bounded by the range buttons (24 h … 90 d) and the bucket step
follows the window, so the *returned* row count is flat while the *scanned* count
grows with the range. A 90-day ingest chart is the expensive case (~26k rows per
device at a 5-minute cadence); a daily `daily`-style rollup for `samples` would be
the next step if that ever matters. The index hint matters here too: `received`
uses `samples_by_time` / `samples_by_device_time`, `device` uses
`samples_by_clock` / `samples_by_device_clock` — without the second pair the
device-time view scans every sample ever stored.

### Writes

D1 counts a row write per B-tree row, so an insert into `readings` costs 3
(the row plus `idx_readings_ts` and `idx_readings_metric`) and a refresh of an
existing timestamp costs 1 — even when the value is identical. Since the
collector re-sends the same provider buckets on every run (CAME's month history,
iLetComfort's hourly energy), that was pure waste.

Both write paths therefore carry a `WHERE` on the `DO UPDATE`, so re-polling a
stored timestamp is a **0-write** statement:

```sql
-- readings: only when the value or unit actually changes
ON CONFLICT(device_id, metric, ts) DO UPDATE SET
  value = excluded.value, unit = excluded.unit
WHERE value IS NOT excluded.value OR unit IS NOT excluded.unit

-- latest: only when the sample is newer, or the same ts with a new value
ON CONFLICT(device_id, metric) DO UPDATE SET
  ts = excluded.ts, value = excluded.value, unit = excluded.unit
WHERE excluded.ts > latest.ts
   OR (excluded.ts = latest.ts
       AND (excluded.value IS NOT latest.value OR excluded.unit IS NOT latest.unit))
```

`IS NOT` rather than `<>` so a NULL value/unit compares correctly. Measured on
the live database: identical re-poll → `rows_read: 0, rows_written: 0`; a
corrected value → 1; an out-of-order sample → 0. `runs.readings_written` keeps
its old meaning (samples the run produced), so it over-reports actual row writes
on a history run — the collector log line is unchanged.

## PWA

`assets/` is an installable Progressive Web App:

| file | purpose |
|---|---|
| `index.html` | app shell — charts, token field, range controls |
| `manifest.webmanifest` | `standalone` display, `theme_color`, 3 icons |
| `sw.js` | service worker |
| `icon-192.png` / `icon-512.png` | any-purpose icons |
| `icon-maskable-512.png` | Android adaptive icon (28% inset, survives circular crop) |
| `apple-touch-icon.png` | 180×180, opaque, for iOS |

Icons are drawn with Pillow, so there is no SVG-delegate dependency and the result is
reproducible. Regenerate after changing the design:

```bash
python3 make-icons.py
```

Service-worker strategy:

- the shell is **precached** on install, so repeat loads are instant and it opens offline
- **navigations are network-first** → a deploy is picked up as soon as you are online
- other static assets are **stale-while-revalidate**
- **`/api/*` is never cached.** This is live sensor data; showing a stale reading as though it
  were current is worse than showing an error. Offline you get the shell plus
  "Offline — showing the cached page; live data unavailable."

Cache name is `v1-shell`. Bump `VERSION` in `sw.js` only when the precache *list* changes —
the HTML refreshes on its own because navigations go to the network first.

Install: Chrome/Android → ⋮ → *Install app*. iOS Safari → Share → *Add to Home Screen*.

## Device ingest

eink-x sensor devices push firmware samples to `POST /v1/samples`, implemented in
`src/ingest.rs` from
[`../../mesh-deepseek/docs/http-endpoint-requirements.md`](../../mesh-deepseek/docs/http-endpoint-requirements.md)
(milestone M1: §4.1, §4.2, §5, §6, §7, §8) plus the v2 deltas from
[`http-endpoint-requirements-v2.md`](../../mesh-deepseek/docs/http-endpoint-requirements-v2.md):
device timestamps, per-batch metadata and the telemetry the admin page shows.

Every accepted sample also shows up on the dashboard: an admin-configured chart
can set `source: "ingest"` and pick either stored clock as its timeline (see
"Chart layout admin"), and the automatic view renders an *Ingested sensors*
section.

```
POST /v1/samples     one batch of 1…64 samples, HMAC-SHA256 signed per device
GET  /v1/health      { ok, time, version, storage } — no auth, `503` if D1 is down
```

`/v1/*` is added to `run_worker_first` in `wrangler.toml`, otherwise the static
assets binding would swallow those paths.

* **Auth** — `X-Signature: v1=<hex>` over
  `"v1\nPOST\n/v1/samples\n<device>\n<boot_id>\n<batch>\n<sha256(rawBody)>"`,
  verified with the device's key and a constant-time comparison. Unknown device
  and bad signature give the same `401 signature_invalid` body. The Appendix A
  vectors are pinned in the unit tests (`cargo test --lib`).
* **Replay / ordering** — `boot_id` + `batch` per device: an exact replay answers
  `200` with `duplicate: N`, a lower batch number `409 batch_out_of_order` with
  `expected_min_batch`, a new `boot_id` restarts the counter. 60 accepted batches
  per device per hour, then `429 rate_limited` with `retry_after` (checked before
  any write).
* **Validation** — request-level problems are `400`/`413`; individual samples are
  dropped with a `problems: [{index, reason}]` list while the rest is stored, so a
  firmware quirk cannot turn into a retry loop.
* **Storage** — one `db.batch()` per request: `INSERT OR IGNORE` into `samples`,
  one `batches_meta` row and the `ingest_devices` update, so a failure commits
  nothing. `received_at` is the Worker clock and is identical for every sample of
  a batch.
* **Device time (v2)** — `sent_at` and `collected_at` are optional and untrusted.
  They land in `batches_meta.sent_at` and `samples.device_collected_at`, never
  over `received_at`; `0`, a missing value or an out-of-range one is stored as
  `NULL` (HR-202/204). A `collected_at` whose length differs from `samples` is
  `400 bad_collected_at`; a `sent_at` more than 24 h ahead (or 400 days behind)
  is `400 implausible_device_time`, while a bad *per-sample* time only nulls that
  column. Every `200` carries `server_time` and `time_source: "server"`.
* **Duplicates (v2 HR-222)** — `(device_id, boot_id, batch)` in `batches_meta` is
  the dedupe key, so a replay is answered `duplicate` even after later batches
  moved the counter; a counter that went *backwards* without a stored batch is
  still `409 batch_out_of_order`.

### Two documented deviations

* The tables are `ingest_devices` / `samples` instead of the document's `devices`
  — that name is already used by the cloud-discovered devices in this database.
* `ingest_devices.key_enc` holds the 32-byte device key as lowercase hex. The
  document allows skipping the AES-GCM + `KEY_PEPPER` encryption **if the decision
  is documented** (§5.1); it is a single-operator deployment with one database, so
  the extra key-management path was left out. If this ever grows past that, that
  is the thing to change first.

### Provisioning a device

Key distribution is out of scope in the document (§1.3), so the operator registers
the device. Easiest is the admin page: open `/admin`, unlock with `API_TOKEN`,
enter the device's BLE address (12 hex, no colons) under *Device ingest* and press
**Register & generate key** — the key appears once, ready to copy into the BLE
config (characteristic `6e40000b`).

Without a browser, the same thing over the API:

```bash
curl -sS -X POST https://<worker>/api/ingest/devices \
  -H "Authorization: Bearer $API_TOKEN" -H 'content-type: application/json' \
  -d '{"id":"E5983C9E9E32","name":"bench node","role":"direct"}'
# → {"ok":true,"device":{…},"key":"<64 hex, shown once>"}
```

Or straight into D1 (offline, e.g. from a script):

```bash
./scripts/fake-device.py --key <64 hex chars> provision | wrangler d1 execute monitoring --remote --file=/dev/stdin
```

`scripts/fake-device.py` also implements a fake device: `vector` prints the
Appendix A signatures, `post` sends one signed batch, `test` runs AT-1…AT-14, and
`reset` prints the SQL that clears the ordering state and the rate window so the
suite can run again. Against `wrangler dev` (plain HTTP on loopback is the
documented dev exception):

```bash
wrangler d1 execute monitoring --local --file=schema.sql
./scripts/fake-device.py provision | wrangler d1 execute monitoring --local --file=/dev/stdin
npx wrangler dev --local &
./scripts/fake-device.py --url http://127.0.0.1:8787 test
```

## Known constraints

- **iLetComfort allows one session per account.** Every login signs the phone app
  out. Prefer a second account with the heat pump shared to it; see
  `../docs/api-research.md` ("login war").
- **CAME TH/700 has no server-side room-temperature history.** The 15-minute poll
  is the data source; we roll our own daily aggregates.
- The C3 sensor frame on this heat pump is a known placeholder — no water
  in/out, outdoor ambient, or compressor data via that path.
- The "Ambient T average" shown in the app is not yet extracted.
